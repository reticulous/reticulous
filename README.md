# reticulous — the buildable

`reticulous/reticulous` is just one component of the [**Reticulous**](https://github.com/reticulous) project: the **buildable**, the straddle that assembles a device image. It is not the whole system — the Reticulum stack, the radio/IP interfaces, and the messaging and browsing apps each live in their own straddles. For what Reticulous is, why Reticulum, and the full family of components, read the **[org README](https://github.com/reticulous)**.

## What this straddle does

The buildable carries no firmware or board HAL of its own — it is the assembly point. It ships the browser SPA, the LittleFS data image, and the LCD launcher icons, and it pulls in the whole reticulous straddle family plus the spangap platform (the base runtime, the IP/web stack, and the on-device LCD UI). You build it *with* a board, which supplies the pin maps, bring-up hooks, and hardware kconfig (flash size, PSRAM mode, display).

It also ships the on-device user manual (`esp-idf/data/webroot/WELCOME.md`), which overrides the viewer straddle's generic welcome page as the viewer's home document. It lives under `esp-idf/` (registered via `SPANGAP_EXTRA_DATA_DIRS` in `esp-idf/CMakeLists.txt`), tracked beside the source, while the SPA build regenerates its own webroot inside each build dir.

Every component starts automatically when it is in the build — there is no hand-written init sequence. The whole entry point is generated by the build from each staged straddle's declared hooks (see [INTERNALS.md](INTERNALS.md)).

## First-run setup, on a device with a screen

A fresh node needs the same answers however you reach it: an admin password, a name, a network, and — where there is a radio — a frequency and a modem configuration. The browser flasher asks for the first three over serial while the device is still on the cable; on a board with a screen the device asks for all of them itself, so a node handed to someone with neither cable nor browser is set up from its own panel.

It is one modal layer over the shell — above the status bar and the home-bar strip, so nothing behind it is reachable — carrying one step at a time:

```
password -> hostname -> network -> [network password] ->
             [LoRa frequency -> LoRa modem] -> [mesh name] -> (gone)
```

The bracketed steps are conditional, and that is the shape of the thing: a step appears when the device still has that question open, and never otherwise.

Every step has **Skip**, and Skip means *on to the next one*, not *abandon the rest*: the answers are independent, and a node that wants a password but no network is an ordinary thing to want. The exception is the LoRa pair, which is one decision in two windows — skipping the frequency skips the modem window with it, because a modem configuration on a radio with no frequency configures nothing.

**Suggest one** on the password step generates a password and shows it in the clear: this screen is its only copy, so it has to be readable long enough to be written down — and copied without one character being mistaken for another. The alphabet pays for that rather than the reader. Out go the pairs that fail at panel size or in handwriting — `l 1 I`, `O 0`, `S 5`, `B 8`, `Z 2`, `u v` — and every letter whose capital is just a bigger copy of its lowercase, which is why the case that survives is only where the two shapes genuinely differ. What is left is 32 characters, and 14 of them is 70 bits: far past anything that will be thrown at a device's admin login, and a password nobody has to squint at.

Every field in the wizard is set in larger type than the chrome around it, for the same reason: these are typed into, checked against a piece of paper, and read back across a desk.

**The network step is the list and nothing else** — no fields competing with it for the panel, so it shows what the scan actually found. Rows **select**; they do not act. A scroll that ends on a row, a trackball that drifts, a click meant for the row above — none of them can commit anything, because committing is the button at the bottom and always was, and the only state a mis-touch leaves behind is a highlight you can see. The selection is held by **name**, so it stays put when the scan republishes every 20 s in a different order. Going on from a network marked **(open)** joins it and no password is ever asked for; any other row, or **Other network…** at the bottom (the only way to a hidden SSID), leads to a step that asks for just what is still missing. Only the open ones are marked, and in a word: nearly every network wants a password, so saying so on every row is noise, and a symbol on the ones that do is a legend the screen has nowhere to put.

Every step has **Back**, on the left of the row and absent only where there is no earlier step to return to. It changes nothing but which step is up: what an earlier step committed stays committed, so walking back into the password step is how you *change* the password, not how you undo it — the wizard remembers the one it set so `authPasswd` can be given it as the current one.

A field that opens holding a value the device already has (the hostname, the mesh name) shows it **as selected text is shown everywhere else**: white on the accent behind the glyphs — a real LVGL text selection, not a filled field, because a filled field is a button — and with no caret. The missing caret is half the message — a field with a cursor blinking in it is asking to be added to, while a highlighted block with none is a thing that will be replaced. The first key that isn't navigation clears it and lands in an empty field; clicking into it settles it for editing instead, exactly as a click drops a selection.

The wizard keeps its own **focus group** while it stands, with the keypad pointed at it. Arrow keys can then only reach its own widgets rather than the launcher tiles behind an opaque layer — and, the reason it matters on the way out, LVGL moves focus to the next object in the group as each one is deleted and scrolls that object into view. Sharing the shell's group meant tearing the wizard down landed focus on some launcher tile and paged the launcher to wherever that tile lived; the keys go back to the shell's group, still on what the shell left focused, so setup hands back the launcher's first page.

**LoRa frequency** is its own window: the number in MHz in a display far larger than an ordinary field — it is the one value on the device that gets read off the screen and compared against another node's — over an on-screen keypad with `.` and backspace, so a board with no keyboard can still type it. That window lays its own buttons out: the keypad wants every row of height it can get, so **Skip** and **Next** move into a column beside it rather than a strip under it, with Next at the bottom where the thumb already is after the last digit. **LoRa Modulation** follows with SF (5–12), bandwidth (125/250/500 kHz) and coding rate (4/5–4/8) as single-choice rows, plus **Enable SUPE** and, directly under it, **Regime** on builds that carry SUPE — the regime is not a second decision to postpone, since a node speaking SUPE on a different channel raster from its neighbours negotiates nothing. Its OK is the only place the radio is switched on (`s.lora.0.enable`), so an abandoned or skipped pair leaves it off rather than on a frequency nobody confirmed.

**Your name on the mesh** is last: the display name an LXMF identity announces itself under — what others on the mesh see when they browse around or message you. It opens **empty**, and deliberately not on the hostname: a hostname is what this box answers to on a network, while this is what a *person* is called on the mesh, and the device has no way to know that. Its OK hands `lxmf.cmd.identity_new` to lxmf, which allocates the slot and generates the keypair. Going without an identity is a decision, and **Skip** is how it is made: an empty field under "Create identity" says so, because it is a mis-press far more often than an answer. The password step reads the same way. It is asked only where there is no identity yet, and only in a build that carries messaging.

### Telling flashmon to stand down

Every boot, before it decides anything, this straddle logs `setup: on-device`. That line describes the *build*, not the boot: this image asks a fresh node's questions on its own screen. A flasher on the other end of the cable reads it and asks nothing — two surfaces asking for one password at the same moment is a race nobody can call, and the board in the operator's hands wins it by default. It is logged during the init walk, so it lands before `spangap ready`, which is what lets a flasher wait for the end of the walk and know for certain whether it is coming.

Each answer goes out through the surface that already owns it — `authPasswd("admin", …)`, `s.net.hostname`, net's `wifi.cmd.add` command key, for the radio `lora.0.freq_mhz` / `lora.0.bw_khz` (iface-lora's own unit bridge converts them to the stored Hz) alongside `s.lora.0.spreading_factor` and `s.lora.0.coding_rate`, and for the mesh name lxmf's `lxmf.cmd.identity_new` — the same paths the browser and the CLI use, so there is no separate provisioning state to reconcile.

The screen is not the only way to answer, either: the browser, the CLI and flashmon can all put the device on a network while the wizard stands. The wifi step watches the link and takes that as its answer, moving on by itself. That matters beyond tidiness — the step keeps a scan armed (`wifi.scan`), and net runs its periodic re-scan **even while associated**, which on a one-radio part costs the association and takes it back roughly every 20 s. A wifi step left standing over a link somebody else established is a join/rejoin cycle, so it doesn't stand.

Finishing **flushes the store twice**: once as the screen is handed back, and again a few seconds later. The wizard's own writes are safe after the first, but everything it hands to another task — net writing `s.net.wifi.nets.<n>` when it takes `wifi.cmd.add`, iface-lora converting `lora.0.freq_mhz` into the stored Hz, lxmf writing an identity and its private key — lands *after* it, and storage's own deadline is a minute from the first dirty write. A device switched off inside that minute would come back with the password and the hostname and none of the rest, which is the worst possible half.

It opens only on a node that still has one of these open — no admin password, no saved network, no radio frequency (a frequency has no default: it is the antenna and the region, which no build can know), no LXMF identity — and only until it has been answered once: reaching the end, by answering or by skipping, sets `s.onboard.done` and it never opens again. A factory reset clears the store, so a factory-fresh node asks again.

A step opens as what it is — the question, its fields, and Skip — on every device. Where there are keys (`lcdSetHasKeyboard`) focus rests on the first field, so the answer is typed straight in and Enter walks to the next one. Where there are none, a tap on a field raises the lcd component's on-screen keyboard over it and its ✓ is that same Enter: the first password hands the keyboard to the retype, the network name to its password. Nothing is put up over the step unasked — the keyboard covers the question it is asking.

The screen is held dark from boot until the launcher's icons settle, and on a fresh node the layer normally goes up inside that window — so the launcher is not what appears first. The code is `esp-idf/main/conditional/spangap-lcd/src/onboard_lcd.cpp`, compiled only when a screen is in the build; a headless board ships none of it.

## Building

The `hw-*` board straddles don't decide what the device does — they only make a board usable. Build the buildable *with* one:

```sh
spangap build reticulous/reticulous --with spangap/hw-lilygo-tdeck      # LilyGo T-Deck Plus (has a screen → on-device UI)
spangap build reticulous/reticulous --with spangap/hw-heltecv4   # Heltec WiFi LoRa 32 V4 (headless)
spangap build reticulous/reticulous --with spangap/hw-meshnology-w12  # Meshnology W12 (LR2021, 30 dBm, OLED status pages)
spangap build reticulous/reticulous --with spangap/hw-lilygo-tbeam-supreme  # LilyGo T-Beam S3 Supreme (AXP2101 rails, GNSS, RTC, OLED status pages)
spangap build reticulous/reticulous --with spangap/hw-wismesh-tap-v2  # RAK WisMesh TAP V2 (touch screen → on-device UI, GNSS)
spangap build reticulous/reticulous --with spangap/hw-waveshare-28b  # Waveshare ESP32-S3-Touch-LCD-2.8B (480x640 touch screen, no radio but WiFi/BLE)
```

The full board list is `spangap/hw-*` in the workspace; each board's own README
says what is wired and what is not.

A board with a screen additionally installs the on-device LCD UI itself, so a screenless board builds headless with no extra flags. Leave off `--with` for a generic build that runs Reticulum over WiFi on any ESP32-S3 with PSRAM — browser and CLI access, but no mesh radio.

One board is not a board: `--with spangap/hw-linux` builds the same firmware for
ESP-IDF's Linux host target, so a station is a process and several of them talk
over a virtual radio on one machine. That is the simulated testbed: `spangap
sim` starts it and opens a map of the network in your browser, where stations
are put down, dragged about and driven. It is for development and testing
rather than for running this software on a Linux box — see
[`sim/README.md`](sim/README.md).

Primary target is the **LilyGo T-Deck Plus** (ESP32-S3FN16R8, 16 MB flash, 8 MB octal PSRAM, SX1262 LoRa, 320×240 LCD, QWERTY, trackball, GPS); the **Heltec WiFi LoRa 32 V4** is a headless secondary. PSRAM is required — the Heltec V3, which has none, does not qualify.

## Security

The design has had dedicated attention on security and is intended to be securable, but the code as it stands should not be relied on where a life depends on it being unhackable.
